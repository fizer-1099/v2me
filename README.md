# V2Ray Config App (Android)

یک اپ اندروید برای مدیریت کانفیگ‌های V2Ray/Xray (لینک‌های `vmess://` و `vless://`) و اتصال واقعی VPN با استفاده از موتور متن‌باز Xray-core (از طریق کتابخانه AndroidLibXrayLite).

## این پروژه چیه و چیه نیست
- **هست:** یک اسکلت کامل و قابل‌کامپایل اندروید استودیو، با:
  - مدیریت لیست کانفیگ‌ها (افزودن با پیست کردن لینک، حذف)
  - پارس کردن لینک‌های vmess/vless به کانفیگ JSON مناسب Xray
  - یک `VpnService` واقعی که TUN اندروید را برقرار می‌کند و آن را به Xray-core وصل می‌کند
- **نیست:** یک APK آماده نصب. باید خودت با Android Studio بیلدش کنی، چون این محیط نه اینترنت دارد نه Android SDK.

## قبل از بیلد باید چکار کنی
1. پروژه رو با **Android Studio (Hedgehog+)** باز کن.
2. فایل `app/build.gradle` — خط مربوط به `AndroidLibXrayLite` رو چک کن. من یک coordinate جیت‌هاب گذاشتم اما بسته به تاریخ، ممکنه نیاز باشه خودت طبق README پروژه اصلی (https://github.com/2dust/AndroidLibXrayLite) روش دقیق افزودنش (AAR لوکال یا jitpack) رو آپدیت کنی. API دقیق کلاس `V2RayPoint` هم بین نسخه‌ها کمی فرق می‌کنه، پس `V2RayVpnService.kt` رو با نسخه‌ای که نصب می‌کنی تطبیق بده (اسم متدها مثل `configureFileContent`, `runLoop`, `domainName`).
3. Gradle Sync بزن تا وابستگی‌ها دانلود بشن (نیاز به اینترنت).
4. روی گوشی/شبیه‌ساز اندروید ۷+ (API 24+) اجرا کن.

## جریان کار در اپ
1. اپ رو باز کن → دکمه `Subscription` → لینک raw از یه ریپوی گیت‌هاب (یا هر URL متنی) که لیست کانفیگ‌هاست رو بذار.
2. اپ خودش لیست رو می‌گیره، پارس می‌کنه، رو همه‌شون تست پینگ (TCP connect) موازی می‌زنه، و اگه "Auto-connect" فعال باشه (پیش‌فرض روشنه) خودش به سریع‌ترین سرور در دسترس وصل میشه.
3. این کار هر بار که اپ باز میشه خودکار تکرار میشه؛ دکمه `Refresh + Ping` هم همینو دستی اجرا می‌کنه.
4. می‌تونی هر کانفیگ رو دستی هم با تپ روی آیتمش وصل کنی (پینگ هرکدوم کنار اسمش نشون داده میشه).
5. دکمه Disconnect بالای صفحه، وصل رو قطع می‌کنه.

## فرمت لیست ساب‌اسکریپشن
یه فایل متنی (یا base64 اون) که هر خطش یه لینک `vmess://`، `vless://` یا `ss://` باشه — همون فرمت رایج که اکثر ریپوهای گیت‌هابی کانفیگ استفاده می‌کنن (raw.githubusercontent.com/.../configs.txt).

**نکته امنیتی مهم:** هرکسی که سرورهای اون لیست رو کنترل کنه، تئوریاً می‌تونه ترافیک عبوری از پروکسی رو ببینه (این محدودیت ذاتی هر VPN/پروکسیه، نه فقط این اپ). فقط از منبعی استفاده کن که بهش اعتماد داری؛ این اپ به‌صورت پیش‌فرض هیچ ریپوی خاصی رو پیشنهاد یا هاردکد نمی‌کنه — خودت باید URL رو وارد کنی.

## محدودیت تست پینگ
تست فعلی فقط **زمان برقراری اتصال TCP خام** به آدرس:پورت سرور رو اندازه می‌گیره، نه سرعت واقعی از پشت پروکسی رمزنگاری‌شده (اون کار نیاز داره واسه هر کاندید جدا engine رو روشن کنی که کند و مخل اتصال فعلیه). این روش برای رتبه‌بندی سریع بین چند سرور خوبه، ولی تضمین دقیق سرعت واقعی نیست.

## نمایش کشور IP خروجی
بعد از وصل شدن، اپ چند ثانیه صبر می‌کنه (تا تونل بالا بیاد) و بعد از طریق همون پروکسی سوکس (نه اینترنت مستقیم گوشی) یه درخواست به ip-api.com می‌زنه تا IP و کشور واقعی خروجی رو نشون بده — دقیقاً همون چیزی که سایت‌های مقصد می‌بینن. اگه این کار رو مستقیم بدون پروکسی انجام می‌دادیم، IP واقعی گوشی نشون داده می‌شد نه IP سرور.

## Smart Test: بهترین سرور برای هر اپ فیلترشده
واقعیت اینه که هر سرویس (کلود، اینستاگرام، یوتیوب، تلگرام و...) ممکنه با IP/کشور متفاوتی بهتر جواب بده — نه یه رتبه‌بندی عمومی واحد. دکمه **Smart Test**:

1. هر کانفیگ ذخیره‌شده رو یکی‌یکی، **جدا از VPN فعال فعلی**، روی یه پورت محلی تستی (نه پورت 10808 که VPN ازش استفاده می‌کنه) به‌عنوان یه پروکسی سوکس مستقل بالا می‌آره.
2. برای هرکدوم، به لیستی از سایت‌های هدف (claude.ai, instagram.com, youtube.com, web.telegram.org, web.whatsapp.com, x.com) یه درخواست HEAD از *داخل همون پروکسی* می‌زنه و تاخیر واقعی رو اندازه می‌گیره.
3. اون سرور رو خاموش می‌کنه، میره سراغ بعدی — پس این فرآیند نه VPN فعال رو قطع می‌کنه، نه با اون تداخل داره.
4. در آخر، یه جدول نشون می‌ده: برای هر اپ، کدوم سرور (با کدوم remark/کشور) سریع‌ترین جواب رو داده.

**نکته:** چون تست‌ها به‌ترتیب و یکی‌یکی انجام میشن (هر کدوم حدود چند ثانیه طول می‌کشه)، با تعداد زیاد سرور ممکنه کل فرآیند چند دقیقه طول بکشه.

## مدیریت سایت‌های تست (دکمه Manage Apps)
تو دیالوگی که با این دکمه باز میشه:
- سایت‌های پیش‌فرض (کلود، اینستاگرام، یوتیوب و ...) رو می‌تونی با تیک روشن/خاموش کنی (بدون حذف کامل).
- می‌تونی سایت دلخواه خودت رو با اسم و URL اضافه کنی (مثلاً بانک، سایت کاری و غیره).
- سایت‌های دلخواه اضافه‌شده رو با آیکون سطل زباله می‌تونی حذف کنی.
- همه این تنظیمات ذخیره میشن و دفعه بعد که Smart Test بزنی همینا استفاده میشن.

## نکات مهم
- الان `vmess://`، `vless://` و `ss://` (Shadowsocks) پشتیبانی میشن.
- کد فعلی امنیت پایه (ذخیره‌سازی رمزنگاری‌شده، قفل با پین و ...) نداره؛ کانفیگ‌ها در SharedPreferences ساده ذخیره میشن.
- قبل از انتشار عمومی، حتماً Terms of Service گوگل پلی درباره اپ‌های VPN رو بخون — پلی استور قوانین سخت‌گیرانه‌ای برای این دسته داره (افشای دقیق سیاست حریم خصوصی، لاگ نکردن ترافیک و غیره).

## چی برای اینترنت ایران اضافه/بهتر شد

1. **پشتیبانی از REALITY** (`security=reality` در لینک vless، با پارامترهای `pbk`, `sid`, `fp`, `spx`, و `flow=xtls-rprx-vision`)
   REALITY به‌جای گواهی TLS واقعی روی سرور خودت، هویت TLS یه سایت واقعی و معروف رو "قرض" می‌گیره، پس دیده‌بان شبکه یه هندشیک TLS کاملاً عادی می‌بینه. الان بهترین گزینه در برابر DPI فعال (active probing) هست. **برای استفاده از این، باید یه سرور Xray با تنظیمات REALITY داشته باشی** (این اپ فقط کلاینتشه).

2. **گزینه Fragment در دیالوگ افزودن کانفیگ** (تیک "Enable TLS fragmentation")
   پکت اول TLS (ClientHello) رو به چند تکه کوچیک با تاخیر تصادفی می‌شکنه، که DPI‌هایی که بر اساس شکل/سایز همون پکت اول تشخیص می‌دن رو گیج می‌کنه. این روی هر پروتکلی (vmess/vless/ss) قابل‌فعال‌سازیه و هزینه‌ای جز کمی افزایش تاخیر نداره.

3. **پشتیبانی از gRPC** به‌عنوان transport، چون تو بعضی شرایط بهتر از WebSocket از فیلترینگ عبور می‌کنه.

4. **DNS بر پایه HTTPS (DoH به 1.1.1.1)** به‌جای DNS معمولی، تا از مسموم‌سازی/بلاک DNS توسط ISP جلوگیری بشه.

5. **Sniffing فعال روی inbound** تا روتینگ بر اساس دامنه واقعی انجام بشه نه فقط IP.

### توصیه‌های عملی (مستقل از کد)
- سرورهایی که IP‌شون تازه‌ست و پشت CDN (مثل Cloudflare) با دامنه‌ی غیرمشکوک هستن معمولاً بیشتر دوام میارن.
- پورت 443 رو ترجیح بده (شبیه ترافیک HTTPS معمولیه).
- اگه یه کانفیگ مسدود شد، معمولاً IP/دامنه سوخته — سرور رو عوض کن، تنظیمات کد رو "خراب" فرض نکن.
- اگه REALITY در دسترسته، اول اونو امتحان کن؛ در غیر این صورت vless+ws+tls یا ss با fragment فعال گزینه‌های بعدی‌ان.

## پایداری و سرعت (فیل‌اُور خودکار)

این بخش‌ها اضافه شدن تا اتصال هم پایدارتر باشه هم سریع‌تر:

**مانیتورینگ مداوم + سوییچ خودکار:** `V2RayVpnService` (سرویسی که VPN رو نگه می‌داره، حتی وقتی اپ بسته‌ست) هر ۲۰ ثانیه یه چک سلامت از *داخل خود تونل* انجام می‌ده (درخواست سبک به یه اندپوینت قابل‌اعتماد). اگه ۲ بار پشت‌سرهم شکست بخوره:
1. سرور فعلی رو "خراب" علامت می‌زنه (و به مدت ۵ دقیقه دیگه امتحانش نمی‌کنه، تا مدام بین یه سرور خراب و بقیه رفت‌وبرگشت نکنه).
2. بین بقیه سرورهای ذخیره‌شده (به‌جز اونایی که تازه خراب شدن) پینگ می‌زنه.
3. بهترین‌شون رو انتخاب می‌کنه و **بدون بستن تونل VPN** موتور Xray رو با کانفیگ جدید ری‌استارت می‌کنه — یعنی نه پرامپت مجوز VPN دوباره میاد، نه اپ‌های دیگه قطعی محسوس می‌بینن.
4. یه نوتیفیکیشن و toast نشون می‌ده که سوییچ خودکار انجام شده.

این کار داخل خود سرویس (نه اکتیویتی) انجام میشه، پس حتی اگه صفحه اپ رو ببندی هم کار می‌کنه.

**تنظیمات خود Xray برای سرعت:**
- **TCP Fast Open** روی هر outbound فعاله — یه رفت‌وبرگشت رو از هندشیک اتصال به سرور پروکسی کم می‌کنه.
- **Mux (مالتی‌پلکسینگ)** فعاله — چندتا کانکشن کوچیک اپ (مثل بارگذاری یه صفحه با عکس/اسکریپت زیاد) از یه کانکشن مشترک به سرور رد میشن، که سربار رو کم می‌کنه. **به‌جز وقتی flow=xtls-rprx-vision باشه** چون REALITY+Vision با mux سازگار نیست (خود مستندات Xray هم همینو میگه).

**نکته درباره Smart Test و failover:** حالا وصله! دکمه Smart Test نتایجش رو ذخیره می‌کنه، و تو همون دیالوگ نتایج می‌تونی یکی از اپ‌ها رو به‌عنوان "اپ اولویت‌دار برای فیل‌اُور" انتخاب کنی (یا "بدون اولویت" بذاری تا فیل‌اُور فقط بر اساس پینگ عمومی کار کنه). وقتی اولویت تنظیم شده باشه:
- موقع فیل‌اُور خودکار (سرور فعلی خراب شده)، اول بین کاندیدها دنبال کسی می‌گرده که تو آخرین Smart Test برای همون اپ اولویت‌دار جواب داده، و سریع‌ترین رو انتخاب می‌کنه.
- اگه داده Smart Test قدیمی‌تر از ۲۴ ساعت باشه، یا هیچ کاندیدی داده معتبر نداشته باشه، خودکار به پینگ عمومی برمی‌گرده.
- همین منطق موقع باز شدن اولیه اپ (auto-connect) هم استفاده میشه، نه فقط تو فیل‌اُور.

## جمع‌بندی نهایی: چیدمان کامل قابلیت‌ها

| قابلیت | جای فعال‌سازی |
|---|---|
| افزودن کانفیگ دستی (vmess/vless/ss) | دکمه `+` |
| ساب‌اسکریپشن خودکار از گیت‌هاب | دکمه `Subscription` |
| تست پینگ عمومی + اتصال خودکار موقع باز شدن اپ | خودکار، یا دکمه `Refresh + Ping` |
| نمایش کشور IP خروجی | خودکار بعد از اتصال |
| تست هوشمند per-app (بهترین سرور برای هر اپ فیلترشده) | دکمه `Smart Test` |
| مدیریت لیست اپ‌های هدف | دکمه `Manage Apps` |
| مانیتورینگ مداوم سلامت + فیل‌اُور خودکار بدون قطع تونل | خودکار، همیشه فعال وقتی وصلی |
| اولویت‌دهی فیل‌اُور بر اساس یه اپ خاص | تو دیالوگ نتایج Smart Test |
| REALITY / XTLS-Vision / Fragment / gRPC / Mux / TCP Fast Open / DoH | خودکار بر اساس پارامترهای لینک هر کانفیگ |

## محدودیت‌های صادقانه (چیزهایی که باید بدونی)
- **این پروژه کامپایل نشده.** من نه SDK اندروید دارم نه اینترنت، پس نتونستم واقعاً بیلدش کنم و روی گوشی تست کنم. منطق‌ها رو با دقت نوشتم و بازبینی کردم، ولی احتمال یه خطای کامپایل جزئی (مثلاً یه mismatch در API دقیق AndroidLibXrayLite) در بیلد اول وجود داره — این طبیعیه، معمولاً با یکی-دو تا تنظیم کوچیک تو Android Studio حل میشه.
- **API دقیق AndroidLibXrayLite ممکنه فرق کنه.** اسم متدهایی مثل `configureFileContent`, `runLoop`, `domainName`, `stopLoop` رو از مستندات عمومی این کتابخانه گرفتم؛ اگه نسخه‌ای که نصب می‌کنی فرق داشته باشه، `V2RayVpnService.kt` و `SmartAppTester.kt` جاهایی هستن که باید تطبیقشون بدی.
- **فرض کردم `shutdown()` ممکنه از `stopLoop()` صدا زده بشه** (رفتار رایج تو کتابخونه‌های مشابه) و یه گارد (`isSwitchingEngine`) براش گذاشتم تا سوییچ خودکار سرویس رو کامل خاموش نکنه. اگه رفتار واقعی کتابخونه فرق داشت، این بخش رو تست کن.
- تست پینگ (چه عمومی چه Smart Test) واقعیت شبکه لحظه‌ای رو می‌سنجه، نه یه پیش‌بینی قطعی — تو شرایط فیلترینگ پویا (که تو ایران رایجه) ممکنه نتایج بین چند دقیقه فرق کنن.

## به‌روزرسانی مهم: کتابخونه API‌شو عوض کرده (تایید شده با جستجوی زنده، آگوست ۲۰۲۶)

بعد از اینکه اولین نسخه این پروژه رو نوشتم، با ابزار جستجوی وب مستندات زنده‌ی AndroidLibXrayLite رو چک کردم و متوجه شدم که کتابخونه (نسخه منتشرشده در ۲۰ آگوست ۲۰۲۶) API‌ش رو کاملاً عوض کرده. کد این پروژه الان با API **جدید** بازنویسی شده:

**چی عوض شد:**
- ❌ قدیم: `V2RayPoint` / `newV2RayPoint(supportSet, bool)` / `configureFileContent` / `runLoop()` / `V2RayVPNServiceSupportsSet` (با `protect()`, `setup()`, `prepare()`)
- ✅ جدید: `CoreController` / `Libv2ray.newCoreController(callbackHandler)` / `controller.startLoop(configJson, tunFd)` / `controller.stopLoop()` / `CoreCallbackHandler` (فقط `startup()`, `shutdown()`, `onEmitStatus()` — **دیگه `protect()` وجود نداره**)

**پیامدهای مهم این تغییر:**

1. **فایل دیسکریپتور TUN مستقیم داده میشه.** به‌جای اینکه خودمون یه tun2socks بنویسیم و از یه سوکس محلی پروتکت‌شده استفاده کنیم، حالا `vpnInterface.fd` مستقیم به `startLoop(configJson, tunFd)` پاس داده میشه؛ خود Xray-core (که یه inbound از نوع `"protocol": "tun"` تو کانفیگ JSON داره) مستقیماً پکت‌های خام IP رو از اون fd می‌خونه/می‌نویسه. این معماری رو از مستندات زنده‌ی `XTLS/Xray-core/proxy/tun/README.md` تایید کردم.

2. **چون `protect()` دیگه وجود نداره، به یه راه‌حل جایگزین نیاز بود.** وقتی VPN با `addRoute("0.0.0.0", 0)` همه ترافیک رو می‌گیره، اتصال خروجی خود Xray-core (که داخل همین پروسه اپ اجرا میشه) به سرور پروکسی واقعی هم می‌افته تو تله‌ی همون تونل و لوپ بی‌نهایت می‌سازه. راه‌حلی که پیاده کردم: `builder.addDisallowedApplication(packageName)` — یعنی *کل پکیج خود اپ* رو از مسیریابی VPN مستثنی می‌کنیم، پس هر سوکتی که این پروسه باز کنه (چه کاتلین چه Xray داخلی) خودکار از تونل رد نمیشه. این یه تخمین معماری منطقیه بر اساس شواهدی که پیدا کردم (از جمله یه پروژه دیگه که همین مشکل «loop» رو با «protect-first outbound protection» حل کرده بود)، ولی **حتماً موقع تست روی گوشی واقعی چک کن که لوپ پیش نمیاد و ترافیک واقعاً از پروکسی رد میشه** (مثلاً با چک کردن IP خروجی که خودمون تو اپ داریم).

3. **تست latency خیلی ساده‌تر و دقیق‌تر شد.** کتابخونه یه تابع آماده داره: `Libv2ray.measureOutboundDelay(configJson, url)` — یه درخواست واقعی از پشت همون کانفیگ (شامل هندشیک TLS واقعی) می‌زنه و تاخیر واقعی رو برمی‌گردونه. این جایگزین شد با:
   - `PingTester.kt`: به‌جای TCP-connect خام به سرور، حالا واقعاً از پشت پروکسی تست می‌کنه — محدودیتی که قبلاً تو README نوشته بودم («فقط TCP خامه، نه سرعت واقعی پروکسی») **دیگه وجود نداره**.
   - `SmartAppTester.kt`: دیگه لازم نیست خودمون یه engine جدا رو روی یه پورت تستی بالا بیاریم و خاموش کنیم؛ فقط `measureOutboundDelay` رو صدا می‌زنیم. کد خیلی ساده‌تر و قابل‌اعتمادتر شد.

4. **`InitCoreEnv(envPath, key)` باید یه بار در طول عمر پروسه صدا زده بشه** قبل از هر استفاده‌ای از کتابخونه (چه VPN چه تست latency). این تو `XrayEnv.kt` به‌صورت singleton پیاده شده. این تابع مسیر فایل‌های asset (`geoip.dat`, `geosite.dat`) رو تنظیم می‌کنه — **این پروژه اون فایل‌ها رو شامل نمیشه** (باینری‌ان و نمی‌تونستم از سندباکس بدون اینترنت دانلودشون کنم). بدون این فایل‌ها، پروکسی ساده (بدون routing rule بر پایه geoip/geosite) باید کار کنه، ولی برای قوانین مسیریابی پیشرفته باید خودت از https://github.com/Loyalsoldier/v2ray-rules-dat دانلود کنی و تو `app/src/main/assets/` بذاری.

**صداقت درباره این تغییر:** من این معماری جدید رو با جستجوی زنده تایید کردم (مستندات pkg.go.dev، سورس واقعی `libv2ray_main.go`، و README رسمی `Xray-core/proxy/tun`)، ولی چون همچنان نمی‌تونم واقعاً کامپایل/تست کنم، چندتا جزئیات (خصوصاً نام دقیق متدهای Kotlin که gomobile تولید می‌کنه، و اینکه `addDisallowedApplication` واقعاً کافیه یا نه) حدسیاتی هستن که باید موقع بیلد اول تو Android Studio تاییدشون کنی. اگه اسم متدی که IDE پیشنهاد می‌ده با چیزی که تو کد نوشتم فرق داشت، احتمالاً فقط یه تغییر حروف بزرگ/کوچیکه، نه یه مشکل معماری.

## گرفتن APK قابل نصب، بدون نیاز به Android Studio

چون من نه SDK اندروید دارم نه اینترنت، نمی‌تونم خودم `.apk` بسازم — فقط سورس‌کد رو نوشتم. ولی یه فایل GitHub Actions (`.github/workflows/build-apk.yml`) تو پروژه گذاشتم که این کارو خودکار انجام می‌ده، رو سرورهای گیت‌هاب:

### مراحل
1. یه ریپوی جدید تو GitHub بساز (خصوصی یا عمومی، فرقی نداره).
2. کل پوشه `V2RayConfigApp` رو توش push کن:
   ```
   cd V2RayConfigApp
   git init
   git add .
   git commit -m "Initial commit"
   git branch -M main
   git remote add origin https://github.com/<username>/<repo-name>.git
   git push -u origin main
   ```
3. برو تو ریپو، تب **Actions** رو باز کن — Workflow به اسم «Build debug APK» خودکار شروع میشه (چون رو push به `main` تریگر میشه).
4. صبر کن تا سبز بشه (چند دقیقه طول می‌کشه، چون هم Android SDK هم Gradle رو از صفر نصب می‌کنه).
5. رو همون run کلیک کن → پایین صفحه بخش **Artifacts** → فایل `v2ray-config-app-debug` رو دانلود کن. یه zip حاوی `app-debug.apk` بهت می‌ده.
6. اون apk رو به گوشیت منتقل کن (یا مستقیم از مرورگر گوشی از GitHub دانلودش کن) و نصبش کن. چون از Play Store نیست، باید یه‌بار تو تنظیمات گوشی «نصب از منابع ناشناس» رو برای همون مرورگر/اپی که ازش دانلود می‌کنی فعال کنی.

### چیزی که این جایگزینش نمی‌کنه
این APK یه **نسخه debug** هست (بدون امضای release، بدون بهینه‌سازی ProGuard) — برای تست شخصی خودت کاملاً کافیه، ولی برای انتشار عمومی (مثلاً تو Play Store) باید جدا امضا و release-build بشه؛ اگه بهش رسیدی بگو راهنماییت کنم.

همچنین چون هنوز خود من این Workflow رو اجرا نکردم (بازم به‌خاطر همون محدودیت اینترنت)، ممکنه اولین اجرا یه خطای کوچیک بده (مثلاً یه نسخه ناسازگار Android SDK). اگه اینطور شد، پیام خطا رو برام بفرست، از رو همون بدون نیاز به گوشی می‌تونم اصلاحش کنم.
